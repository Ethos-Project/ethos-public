The arXiv route should be approached only after the Eros Genome public-safe language, architecture boundaries, artifact release posture, and authorship/citation metadata are stable.

## Current arXiv facts to verify before any future submission

Before any actual submission work, re-check official arXiv documentation because requirements may change.

Known current points to evaluate:

- arXiv submissions should be topical, refereeable scientific contributions following accepted scholarly communication standards.
- arXiv accepts submissions only from registered authors; new users or new categories may require endorsement.
- Submissions are moderated for appropriateness/topicality.
- Authors must grant arXiv an irrevocable license to distribute the work and agree to the submittal agreement and policies.
- Preferred submission format is TeX/LaTeX; PDF and HTML are possible in defined cases, but arXiv stores portable/stable sources and has strict formatting/file requirements.
- arXiv requires careful title/abstract/metadata preparation and category selection.

Primary docs to re-check:

- https://info.arxiv.org/help/submit/index.html
- https://info.arxiv.org/help/submit_tex.html
- https://info.arxiv.org/help/license/index.html
- https://info.arxiv.org/help/endorsement.html
- https://info.arxiv.org/help/prep.html

## Scope

Create a planning/readiness document for a future arXiv preprint.

The plan should identify:

1. **Paper candidate type**
   - Determine whether the first arXiv-facing work should be:
     - architecture paper
     - methods paper
     - position paper only if eligible/appropriate
     - software systems paper
     - formal technical report
     - companion paper linked to OSF artifacts
   - Verify whether the intended type is acceptable for the selected arXiv category.

2. **Category and endorsement readiness**
   - Identify candidate arXiv categories, likely in computer science / AI / systems / human-computer interaction / machine learning / robotics only if substantiated.
   - Determine endorsement risk and whether an endorser may be required.
   - Do not assume category acceptance.

3. **Claims discipline**
   - Avoid unsupported consciousness, AGI, medical, robotics deployment, regulatory, legal, safety-certification, investment, or performance claims.
   - Prefer defensible language such as:
     - ethical cognition architecture
     - interpretable cognitive governance
     - developmental AI architecture
     - safety-governed orchestration
     - provenance-aware research architecture
     - reproducible architecture roadmap

4. **Paper structure outline**
   - title candidates
   - abstract draft boundaries
   - introduction
   - related work map
   - architecture/methods
   - governance and safety constraints
   - limitations and non-claims
   - reproducibility / artifact availability statement
   - OSF/GitHub reference posture
   - future work

5. **Source package readiness**
   - Determine whether the paper should be authored in LaTeX from the start.
   - Track required files:
     - `.tex`
     - `.bib` or `.bbl`
     - figures with arXiv-compatible naming/case/format
     - no private notes/logs/traces
     - no proprietary or unsafe embedded material
   - Verify source builds locally before any future upload.

6. **Disclosure and release gates**
   - IP / disclosure review completed
   - public terminology reviewed
   - authorship/contributor metadata settled
   - public/private/protected artifacts classified
   - OSF relation determined
   - license posture reviewed
   - category/endorsement route checked
   - no protected runtime exposure risk

7. **Future handoff prompt**
   - Produce a copy/paste-ready prompt for Codex/IDE agent to draft an arXiv readiness document when the project reaches required maturity.
